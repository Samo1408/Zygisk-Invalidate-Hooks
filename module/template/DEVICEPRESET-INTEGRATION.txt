DevicePreset / inline_hook_spoof integration

- inline_hook_spoof keeps its original Zygisk/webroot targeting behavior and config.txt app-target list.
- DevicePreset property application is system-wide and independent from the app-target list.
- Shared property file: /data/adb/modules/inline_hook_spoof/config/device.prop
- Editable source profile: /data/adb/modules/inline_hook_spoof/config/devicepreset-profile.json
- post-fs-data.sh applies properties using the fixed executable path /system/bin/resetprop-rs --stealth.
- The resetprop-rs executable is provided on the device at /system/bin/resetprop-rs; it is not bundled or searched for inside the module.
- Results, including getprop read-back verification, are logged to /data/adb/modules/inline_hook_spoof/last_apply.log. Read-back verification does not imply that independent framework or hardware APIs report the same value.
- ro.hardware is intentionally disabled because it can cause lock-screen problems; ro.product.hardware, ro.board.platform, and ro.boot.board.platform are also excluded.
- `audit-soc.sh` is a read-only diagnostic for configured/live SoC properties and available kernel-reported SoC/CPU fields.
- `service.sh` retries only `ro.soc.model` and `ro.soc.manufacturer` at bounded checkpoints (0, 2, 5, 10, 20, 30, and 60 seconds) when readback differs, and logs the command exit code, before/expected/after values, and the paired SoC sample. This is a bounded corrective attempt plus diagnosis, not a guarantee that the platform will accept the override.



Zygisk native hooks (step 7)
----------------------------
The native library now compiles native_spoof.cpp into libinline_hook_spoof.so.
For packages enabled in config.txt, main.cpp loads the override files during
preAppSpecialize and installs native PLT/GOT hooks during postAppSpecialize.
The hook layer intercepts imported Bionic property APIs (__system_property_get,
__system_property_find, __system_property_read, __system_property_read_callback,
and __system_property_serial) and imported open/openat/fopen variants.
Property values are sourced from config/device.prop in the selected app process;
CPUINFO_HARDWARE and PROC_VERSION are sourced from config/proc-overrides.conf.
For /proc/cpuinfo, only the Hardware line is replaced; for /proc/version, only
the Linux version token is replaced. Other file paths and non-overridden
properties are forwarded to their original functions.

The original mainCore.cxx restoration implementation is unchanged. Its existing
call remains in preAppSpecialize; the additional native hooks install after app
specialization and are limited to the same config.txt-selected processes.
This is a PLT/GOT import hook, not an inline instruction patch. It affects
already-loaded ELF objects with matching dynamic relocations; libraries loaded
later or code using direct syscalls/internal non-PLT calls may bypass it. Device
runtime validation is still required, and a successful build/log line alone is
not proof that every consumer uses the spoofed values.

- The next diagnostic pass compares Android `getprop` with resetprop-rs's own property read before and after a SoC write. This distinguishes a write/read-path discrepancy from a value that both readers still report unchanged; `rc=0` alone is not treated as verification.

- Step 6: for only `ro.soc.model` and `ro.soc.manufacturer`, the late pass first tries `--stealth`; if Android `getprop` still mismatches, it tries the tool's documented `--init` mode and then the normal setter. Every attempt is verified through Android `getprop` and logged with its mode. The normal setter can notify property listeners; this fallback is limited to those two keys and only runs when prior readback checks fail. Device testing is required to establish which mode works on this ROM.


Native hook diagnostics (step 10)
--------------------------------
- Initial Zygisk installation now logs a per-symbol PLT/GOT patch summary, including each property API and file API with one or more patched slots.
- Newly loaded libraries log the same per-symbol summary when additional slots are patched.
- A nonzero total patched_slots does not prove that the target's property-reading path was intercepted; check whether the relevant __system_property_* symbols have patched slots. A zero count means this PLT/GOT pass did not find any matching relocation slots in currently loaded objects.
- These logs are diagnostic only and do not alter the original mainCore.cxx restoration flow or broaden package targeting.
